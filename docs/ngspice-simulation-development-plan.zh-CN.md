# ngspice 仿真开发计划

## 1. 目标

本计划定义 JLCEDA Suite 引入 `ngspice` 的最小可用仿真路线，目标不是一次性覆盖所有电路类型，而是先把“AI 生成电路 -> 电气验证 -> 结果回写”这条链路打通。

核心目标：

- 让 `CircuitModel` 可以派生出可仿真的连接表示
- 让仿真输入与 JLCEDA 执行计划解耦
- 让仿真失败能够结构化回写到模型与规则层
- 让 agent 不再依赖“默认连法”来掩盖不确定性

## 2. 选择 ngspice 的原因

`ngspice` 适合作为第一阶段的主力仿真器，原因是：

- 开源，可脚本化
- 支持命令行批量执行
- 适合自动化回归和 CI
- 适合中小规模模拟电路验证
- 便于与本仓库的 Python 侧工作流集成

后续如果需要更强的规模能力，可以再评估 `Xyce`；如果个别器件只在厂商生态里有更完整宏模型，再补充 `LTspice` 人工通道即可。

## 3. 作用边界

`ngspice` 主要承担“电气行为验证”，不承担“设计正确性”的全部责任。

它适合验证：

- 偏置是否正确
- 工作点是否合理
- 时域波形是否符合预期
- 频率响应是否符合预期
- 参数变化是否引起明显异常

它不适合单独承担：

- strap / mode 脚的设计依据判断
- 器件选型的工程合理性裁决
- PCB 寄生、EMI、走线耦合的完整评估

这些内容仍然需要规则层、数据手册依据和人工确认共同约束。

## 4. 建议的数据层

推荐的数据链路如下：

```text
RequirementSpec
  -> CircuitModel
  -> Netlist
  -> SPICE Netlist
  -> ngspice
  -> Validation Report
```

其中：

- `CircuitModel` 保存需求、选型、风险、约束和设计依据
- `Netlist` 保存电气连接真值
- `SPICE Netlist` 是仿真器可直接消费的文本输入
- `Validation Report` 保存仿真结果、失败原因和建议动作

## 5. 开发阶段

### Phase 0: 范围定义

先明确第一批支持对象：

- 线性电源
- 基本放大与偏置电路
- RC / RLC 网络
- 简单反馈回路

先明确第一批分析类型：

- `.op`
- `.tran`
- `.ac`

### Phase 1: Netlist schema

定义仓库内部的 `Netlist` 数据结构。

最少包含：

- 元件实例
- 节点
- 引脚映射
- 参数
- 子电路引用
- 设计备注或约束引用

要求：

- 只表达电气连接真值
- 不混入布局信息
- 不混入执行命令

### Phase 2: SPICE 导出器

实现 `Netlist -> SPICE Netlist` 的导出器。

要求支持：

- 基础无源器件
- 常见半导体器件
- `.param`
- `.model`
- `.subckt`
- `.include`

导出器必须处理：

- 地节点归一化
- 参数缺失报错
- 未确认连接显式标记
- 无法表达的内容拒绝静默降级

### Phase 3: ngspice 执行器

实现一个可脚本化的执行层，负责：

- 写临时仿真文件
- 调用 `ngspice`
- 设置超时
- 收集 stdout / stderr
- 提取工作点、波形和测量结果

优先采用命令行模式，先稳定再考虑更深的库级集成。

### Phase 4: 结果回写

把仿真结果结构化回写到模型层。

建议回写内容：

- `CircuitModel.risks`
- `RequirementSpec` 的待确认项
- 失败代码
- 失败摘要
- 建议的下一步动作

### Phase 5: 回归测试

建立最小回归集，覆盖：

- 简单分压
- RC 低通
- 运放偏置
- 典型电源启动片段

每个回归样例都应包含：

- 输入 netlist
- 预期分析类型
- 预期关键结果
- 允许误差
- 失败时的诊断提示

## 6. 验收标准

第一阶段完成时，应满足：

- 能把一个最小 `Netlist` 导出为合法 SPICE 网表
- 能用 `ngspice` 跑通至少一种分析
- 能把结果结构化保存
- 能把失败信息回写到模型
- 能被仓库中的后续规则层或 skill 流程消费

## 7. 暂不做的事情

以下内容暂不纳入第一阶段：

- 完整替代 JLCEDA 原理图执行层
- 完整 PCB 级寄生建模
- 完整 EMI / SI 仿真
- 复杂大规模并行优化

# KiCad Agent Suite 仓库介绍

KiCad Agent Suite 是一个面向硬件设计协作的自动化工作流仓库，目标不是替代工程师画板，而是把“选型、建模、原理图、校验、迭代”这些原本分散的步骤串成一条可追踪、可复用、可托管的流水线。

这个仓库最核心的思路很简单：

- 用 `circuit-model.json` 作为统一输入
- 让元件选择、符号映射、封装映射、3D 资产、原理图生成和后续校验都围绕这份模型展开
- 用 `where` 进度文件跟踪托管式实施状态
- 用标准化 example 目录承载不同硬件项目

## 这个仓库解决什么问题

传统硬件设计里，很多信息散落在不同地方：

- 器件选型在表格里
- 拓扑逻辑在脑子里
- 原理图在 KiCad 文件里
- 封装和 3D 资源又分散在别的库里
- 设计过程中的风险和待确认项，常常只存在聊天记录或临时笔记中

这会带来几个典型问题：

- 新项目难以复用
- 设计状态不透明
- 自动化工具很难接力
- 复盘时很难追溯为什么这样选

KiCad Agent Suite 想解决的，就是把这些信息重新收束成一个可执行的工程模型。

## 仓库的工作方式

仓库把一个硬件项目拆成四层：

### 1. 需求层

先定义这块板子要做什么，不做什么，哪些接口是必须的，哪些风险必须提前确认。

### 2. 模型层

用 `circuit-model.json` 把需求转成结构化描述，包括：

- 元件
- 网络
- 计算项
- 设计决策
- 风险

### 3. 生成层

由脚本和流水线把模型转换为：

- KiCad 工程
- 原理图结构
- 封装和符号引用
- 可供校验的中间产物

### 4. 校验层

通过 ERC、库校验、3D 资产检查、脚本校验等步骤，尽量在早期发现问题。

## 为什么强调 circuit-model

在这个仓库里，`circuit-model.json` 不是普通配置文件，而是硬件设计的“中间事实层”。

它的作用是：

- 让设计意图结构化
- 让元件选择可追踪
- 让不同阶段的产物共享同一份事实源
- 让自动化工具有机会接手后续步骤

这意味着你不需要一上来就把所有细节都锁死，而是可以先把拓扑、器件角色和关键风险描述清楚，再逐步收敛到工程实现。

## H618 AgentBoard V1 示例

仓库里目前最重要的 example 是 `examples/h618-agentboard-v1`。

它代表的是一块面向 AI Agent 工作流的 H618 Linux 控制开发板，核心目标是：

- MicroSD 启动
- UART 调试
- 以太网
- USB Host
- GPIO / UART / I2C / SPI 扩展
- 预留协处理器接口

这个 example 的意义不只是“做一块板”，更是验证这套工作流能否把一个真实硬件项目从需求一直推进到可落地工程输入。

## 现在已经有哪些能力

当前仓库已经覆盖了很多基础能力：

- 标准化 example 目录骨架
- scaffold 命令
- `circuit-model` 结构规范
- 系统架构、电源树、启动链、pinmux、原理图模块输入等文档

对于 H618 example 来说，仓库已经把前期最耗时的工作大幅前移：

- 需求和接口已收敛
- 拓扑和收口文档已建立
- EasyEDA/JLC 资源链路已打通
- 初版原理图工程已生成

## 这个仓库和普通脚本仓库有什么不同

它不是单纯的“把 JSON 转成 KiCad”。

更准确地说，它是一个把硬件设计工程化的协作底座：

- 可以把设计状态显式记录下来
- 可以把人工判断沉淀成模型
- 可以把流水线输出和人工审查结合起来
- 可以为多个 example 复用同一套方法

仓库里另一套已经匿名化处理的隔离式双芯调试器示例，也在重复验证同一条思路：先把元件来源、库映射、封装和 3D 资源收口，再让工程生成和校验链接手后续工作。这个对比很适合说明，这套方法不是只针对某一块板子，而是可以横向复用到不同类型的硬件项目。

这让它更适合长期迭代，而不是一次性脚本。

## 适合谁

这个仓库适合以下场景：

- 想把硬件设计流程标准化的人
- 想把 KiCad 工程和自动化工作流结合的人
- 想让 AI Agent 参与硬件协作的人
- 想沉淀可复用板卡模板的人

# JLCEDA AIAgent 开发计划

## 目标

将当前仓库从通用模板整理为一个可控的 JLCEDA 扩展，用来作为 Codex 与 JLCEDA 之间的桥接层，使 Codex 可以读取编辑器状态、执行安全的硬件设计操作，并接收结构化结果。

## 产品定位

- 这个仓库不只是一个普通的 JLCEDA 插件。
- 它是一个把 JLCEDA 编辑能力封装成 Codex 可调用硬件能力的桥接层。
- 插件应当暴露受控动作，而不是把底层编辑器 API 直接暴露给模型生成的调用。

## 分阶段计划

### 第一阶段：仓库基础整理

先把模板仓库整理成项目专用工作区。

- 替换 `README`、元信息和社区文档中的模板占位内容。
- 增加简洁的架构说明和仓库目标说明。
- 确定路线图、协议说明和 API 调研文档的存放位置。
- 保留 `.where-agent-progress.md` 作为轻量执行看板。

完成标准：

- 仓库能清楚说明自己的目标、范围和近期里程碑。
- 新加入的协作者能一眼看出这是一个 JLCEDA + Codex 集成项目。

### 第二阶段：JLCEDA 扩展骨架

基于官方 SDK 指南搭建最小可运行扩展。

- 增加 `extension.json`。
- 增加 `src/index.ts` 作为扩展入口。
- 建立 TypeScript 构建输出和打包流程。
- 验证构建产物能够被 JLCEDA 正常导入。

完成标准：

- 插件能够成功构建。
- JLCEDA 能加载扩展并触发入口逻辑。

### 第三阶段：Codex 桥接协议

在实现复杂功能前，先定义 Codex 与插件之间的契约。

- 定义命令类别，例如 inspect、place、wire、annotate、export。
- 定义结构化输入载荷与结构化结果载荷。
- 增加错误码、重试语义和高风险操作确认规则。
- 决定通信方式是轮询、消息总线还是本地文件方式。

完成标准：

- 有一份明确的命令/结果格式说明。
- 最小可用的端到端请求/响应流程达成一致。

### 第四阶段：EDA 能力适配层

将官方 JLCEDA API 封装为内部抽象层。

- 为文档访问、选区读取、器件操作和编辑器反馈建立服务模块。
- 屏蔽编辑器细节，让上层调用稳定的内部方法。
- 对不支持的操作进行检测，并返回清晰失败，而不是产生不安全的部分执行。

完成标准：

- 核心编辑器操作能通过内部适配函数调用。
- 桥接层不再直接依赖分散的原始 API 调用。

### 第五阶段：首个可用硬件工作流

交付一个范围收敛但真实可演示的工作流，用来验证方向。

- 从 JLCEDA 读取当前工程上下文。
- 允许 Codex 放置一小组受支持的器件。
- 允许 Codex 在明确约束下创建简单连接。
- 导出组件清单、连接快照或 BOM 草稿等结果。

建议的首个里程碑：

- “读取当前原理图并放置一个校验通过的器件，同时返回结构化执行结果。”

完成标准：

- 可以演示一次完整的 Codex 到 JLCEDA 的任务闭环。
- 结果可检查、可复现。

### 第六阶段：验证与发布准备

让项目具备可重复使用和交付能力。

- 尽量增加冒烟测试或脚本化校验。
- 增加日志、排障说明和失败示例。
- 增加版本管理规则和发布检查清单。
- 准备示例工程或演示场景，用于上手说明。

完成标准：

- 有一条可重复执行的验证路径。
- 新用户能以较低门槛完成安装、运行和理解。

## 建议架构分层

建议采用以下分层：

1. JLCEDA 扩展宿主层
2. 能力适配层
3. Codex 桥接协议层
4. 硬件工作流层

这样可以把官方 API 细节隔离在底层，也更方便后续演进 Codex 侧命令契约。

## 当前优先事项

建议优先推进以下事项：

1. 替换模板仓库元信息和 README 内容。
2. 补上最小可运行的 JLCEDA 扩展骨架。
3. 起草第一版 Codex 命令协议。
4. 选定一个首个端到端演示工作流。

## 待决策问题

后续需要尽快明确这些问题：

- Codex 如何与本地插件运行时通信
- 哪些 JLCEDA 操作可以在无额外确认下执行
- 如何把工程状态压缩成适合模型使用的结构化表示
- 第一阶段只支持原理图，还是同时覆盖 PCB 操作

# JLCEDA AIAgent 开发计划

## 目标

将当前仓库从通用模板整理为一个完整的双端桥接系统：

- 客户端是一套运行在 JLCEDA 内部的扩展插件
- 服务端是一套部署在公网服务器上的桥接服务

最终目标是让服务器端的 Codex 可以通过桥接服务连接在线的 JLCEDA 插件实例，读取编辑器状态、执行受控硬件设计操作，并接收结构化结果。

## 产品定位

- 这个仓库不只是一个普通的 JLCEDA 插件。
- 它是一个由“JLCEDA 插件端 + 公网桥接服务端”组成的双端系统。
- 插件端负责封装 JLCEDA 编辑能力并执行本地操作。
- 服务端负责会话管理、鉴权、远程请求路由与结果回传。
- 整个系统的目标，是把 JLCEDA 编辑能力封装成 Codex 可调用的硬件能力，而不是把底层编辑器 API 直接暴露给模型。

## 分阶段计划

### 第一阶段：仓库基础整理

先把模板仓库整理成项目专用工作区。

- 替换 `README`、元信息和社区文档中的模板占位内容。
- 增加简洁的架构说明和仓库目标说明。
- 确定路线图、协议说明和 API 调研文档的存放位置。
- 保留 `.where-agent-progress.md` 作为轻量执行看板。

完成标准：

- 仓库能清楚说明自己的目标、范围和近期里程碑。
- 新加入的协作者能一眼看出这是一个 JLCEDA + Codex 集成项目。

### 第二阶段：JLCEDA 扩展骨架

基于官方 SDK 指南搭建最小可运行扩展。

- 增加 `extension.json`。
- 增加 `src/index.ts` 作为扩展入口。
- 建立 TypeScript 构建输出和打包流程。
- 验证构建产物能够被 JLCEDA 正常导入。

完成标准：

- 插件能够成功构建。
- JLCEDA 能加载扩展并触发入口逻辑。

### 第三阶段：Codex 桥接协议

在实现复杂功能前，先定义 Codex 与插件之间的契约。

- 定义命令类别，例如 inspect、place、wire、annotate、export。
- 定义结构化输入载荷与结构化结果载荷。
- 增加错误码、重试语义和高风险操作确认规则。
- 决定通信方式是轮询、消息总线还是本地文件方式。

完成标准：

- 有一份明确的命令/结果格式说明。
- 最小可用的端到端请求/响应流程达成一致。

### 第四阶段：EDA 能力适配层

将官方 JLCEDA API 封装为内部抽象层。

- 为文档访问、选区读取、器件操作和编辑器反馈建立服务模块。
- 屏蔽编辑器细节，让上层调用稳定的内部方法。
- 对不支持的操作进行检测，并返回清晰失败，而不是产生不安全的部分执行。

完成标准：

- 核心编辑器操作能通过内部适配函数调用。
- 桥接层不再直接依赖分散的原始 API 调用。

### 第五阶段：首个可用硬件工作流

交付一个范围收敛但真实可演示的工作流，用来验证方向。

- 从 JLCEDA 读取当前工程上下文。
- 允许 Codex 放置一小组受支持的器件。
- 允许 Codex 在明确约束下创建简单连接。
- 导出组件清单、连接快照或 BOM 草稿等结果。

建议的首个里程碑：

- “读取当前原理图并放置一个校验通过的器件，同时返回结构化执行结果。”

完成标准：

- 可以演示一次完整的 Codex 到 JLCEDA 的任务闭环。
- 结果可检查、可复现。

### 第六阶段：验证与发布准备

让项目具备可重复使用和交付能力。

- 尽量增加冒烟测试或脚本化校验。
- 增加日志、排障说明和失败示例。
- 增加版本管理规则和发布检查清单。
- 准备示例工程或演示场景，用于上手说明。

完成标准：

- 有一条可重复执行的验证路径。
- 新用户能以较低门槛完成安装、运行和理解。

### 第七阶段：服务器端通信架构

在插件端能力已经具备基础闭环后，补齐公网桥接服务的通信设计。

- 采用“插件主动连接公网服务端”的拓扑，避免服务端反向连接本地客户端。
- 明确基础消息类型，例如 `agent.register`、`agent.heartbeat`、`bridge.request`、`bridge.response`、`bridge.event`。
- 约定插件实例标识、会话标识、请求关联 ID 和重连行为。
- 设计第一版鉴权方案，例如预共享 token、设备标识和基础白名单。

完成标准：

- 有一份明确的双端通信设计。
- 插件端和服务端对消息格式和连接生命周期达成一致。

### 第八阶段：服务器端桥接服务实现

实现运行在公网服务器上的桥接服务，为后续 Codex 接入提供稳定入口。

- 搭建 WebSocket 服务端。
- 增加插件注册、在线会话管理和心跳保活。
- 提供命令下发与响应回传能力。
- 提供最小的服务端 API 或内部调用接口，供 Codex 侧接入。

完成标准：

- 服务端可以稳定接收插件连接。
- 可以向指定在线插件会话下发桥接请求，并收到结构化响应。

### 第九阶段：插件端远程传输层

在现有本地桥接处理器之上，加一层远程传输接入。

- 增加插件侧 WebSocket 客户端。
- 在连接建立后向服务端发送注册信息和支持命令列表。
- 将收到的远程 `BridgeRequest` 接入现有 `executeBridgeRequest`。
- 补充连接状态、自检和重连策略。

完成标准：

- 插件端可以稳定连接服务端。
- 插件端可以执行来自远程服务端的结构化桥接请求。

### 第十阶段：端到端远程控制链路

完成服务器端 Codex 到 JLCEDA 的真实远程闭环。

- 本地联调服务端和插件端。
- 验证公网环境下的连接稳定性。
- 验证服务器端 Codex 可以向指定在线插件发送命令。
- 记录真实运行中的错误、延迟和权限边界。

完成标准：

- 服务器端 Codex 可以远程读取 JLCEDA 状态。
- 服务器端 Codex 可以在确认约束下执行基础写操作。
- 远程链路具备最小可用性和可排障性。

## 建议架构分层

建议采用以下分层：

1. JLCEDA 扩展宿主层
2. EDA 能力适配层
3. 插件端桥接协议层
4. 插件端远程传输层
5. 服务端会话与路由层
6. 服务端 Codex 接入层
7. 硬件工作流层

这样可以把 JLCEDA 官方 API、插件端通信实现和服务端会话管理隔离开来，也更方便后续演进 Codex 侧命令契约。

## 当前优先事项

当前建议优先推进以下事项：

1. 明确插件主动连接公网服务端的通信模型和安全边界。
2. 在仓库内搭建第一版服务端桥接程序。
3. 在插件端增加远程传输层并接入现有桥接处理器。
4. 完成一次服务端到 JLCEDA 的端到端联调。
5. 在联调通过后补做 JLCEDA 客户端内的实机验证记录和修正。

## 待决策问题

后续需要尽快明确这些问题：

- 服务端和插件端分别放在同一个仓库还是拆分子目录
- 服务端对 Codex 暴露 WebSocket、HTTP API，还是内部 SDK
- 插件连接公网服务端时使用什么鉴权机制
- 是否允许多台 JLCEDA 客户端同时在线并由服务端选择目标会话
- 哪些 JLCEDA 操作可以在无额外确认下执行
- 如何把工程状态压缩成适合模型使用的结构化表示
- 第一阶段只支持原理图，还是同时覆盖 PCB 操作
